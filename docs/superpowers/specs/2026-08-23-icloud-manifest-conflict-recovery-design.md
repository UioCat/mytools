# iCloud Manifest 冲突恢复与幂等发布设计

> 2026-08-23 历史方案。后续双设备收敛修复、删除标记保留、等价版本判定与自动化验证以 [同步可靠性](../../sync-reliability.md) 为准。

## 背景与根因

当前同步目录存在同一设备、同一代际的两个 `manifest.json` 文件版本：当前版本为
revision 1887，未解决版本为 revision 1885。两个版本引用的快照均完整且哈希有效，
1887 的已见版本向量逐项不小于 1885，因此 1885 是 1887 的祖先，不是分叉数据。

现有发布流程先创建带随机 UUID 的不可变快照目录，再原子替换 `manifest.json`。iCloud
File Provider 保留未解决文件版本后，写入后的回读会因非字节相同冲突而失败；本地 revision
不会提交，下一次重试仍计算出相同 revision，却会创建新的随机目录。由此，同一个 revision
累计产生数万份目录。

问题由三项行为叠加造成：

- 只协调同步根目录，未对实际被替换的 `manifest.json` 做文件级替换协调；
- 只会消除字节完全相同的文件版本，不会识别可证明安全的祖先版本；
- 发布失败后的重试不是幂等操作，且冲突检查晚于快照创建。

## 目标与边界

当前方案应实现：

- 对元数据目标文件执行精确的协调读写，降低 File Provider 产生冲突的概率；
- 仅在证据完整时自动收敛同设备、同代际、单调前进的 manifest 冲突；
- 同一 revision 重试时复用既有快照，失败不会持续增加孤儿目录；
- 通过持久化发布台账，只限量回收能证明从未发布或已被确认版本取代的快照；
- 防止多个 MacTools 进程同时写入同一个同步副本；
- 保持同步协议、剪贴板范围和旧数据读取兼容。

当前方案不改变剪贴板内容 ID、收藏与置顶筛选、合并规则、代际重置、设备移除、
tombstone 或 receipt 语义；不自动覆盖真正分叉的版本，不自动重置整个同步目录，也不在
日志中记录剪贴板内容、真实同步路径或凭据。

## 必须保持的发布约定

1. 快照目录发布后保持不可变，`manifest.json` 仍是副本唯一的当前指针。
2. manifest 必须最后发布；其引用的剪贴板、偏好和 tombstone 文件必须已完成校验。
3. 每台设备只写、恢复和清理自己的副本目录，不修改其他设备的当前 manifest 或文件版本。
4. 普通候选读取不完整、文件未下载或哈希校验失败时，不执行冲突消除或垃圾回收；唯一例外是
   下文严格限定的 `verifiedBySupersededLedger`，且它只能淘汰迟到祖先。
5. 本地 revision 只在 manifest 发布并回读验证成功后提交。
6. “当前未发现 manifest 引用”不是删除证据；manifest 替换一旦开始，相关快照必须按发布
   结果不确定处理，直到后续对账取得确定证据。

## 组件边界

### Core：纯冲突决策

在 `MacToolsCore` 增加可独立测试的 manifest 冲突决策器。输入为当前文件版本、未解决
文件版本及其快照校验结果，输出只有三类：保留当前版本、采用某个冲突版本、无法自动处理。

普通候选版本只有同时满足以下条件，才能参与自动收敛并成为赢家：

- schema、设备 ID 和 generation 相同；
- revision、文件名和三个快照头部字段相互一致；
- 三个快照均可读取、可解码且内容哈希正确；
- 所有 revision 均为非负数，且每个候选的 `seenRevisions[deviceID]` 等于自身 revision；
- 候选版本的 `seenRevisions` 对另一版本逐项不小于，且至少一项更大；
- 所有有效候选中存在唯一的最大版本，且获胜者 revision 不小于任一被淘汰版本。

任一证据缺失、出现多个不可比较的最大版本，或文件仍未下载时，普通验证结果必须是“无法自动
处理”。决策器不直接调用 `NSFileVersion`，也不负责文件删除。

`verifiedBySupersededLedger` 是不需要旧快照仍存在的唯一验证结果，只能在副本所有者本机、
store ID 和 generation 相同、台账状态为 `superseded` 或 `reclaimed`、迟到 manifest 的完整摘要、
snapshotDirectory 和三个声明摘要与台账逐项匹配，且台账记录的取代 revision 正是当前完整
有效赢家或其祖先时产生。该结果只能把迟到文件版本确认为已淘汰祖先；它不得成为赢家、恢复
内容、贡献 `seenRevisions`、参与普通合并或确认任何 outbox。任一字段不符即保留冲突。

### Platform：iCloud 文件版本协调

在 `Sources/MacTools/Platform` 实现 Foundation 文件版本适配器，通过注入协议供
`DriveSyncStore` 使用：

- 对确切的 manifest URL 使用 `NSFileCoordinator` 普通协调写来更新内容；不得仅因底层使用原子
  临时文件替换就采用 `.forReplacing`，该选项只描述逻辑上以不同项目替换目标的操作；
- 枚举 `NSFileVersion` 当前版本与未解决版本；每个历史候选必须协调读取其自身 `version.url`，
  并使用协调器回调给出的 URL 取得内容，再转换为 Core 可验证的数据；
- 只有收到 Core 的确定性选择后才处理文件版本；当前版本获胜时直接回读验证，冲突版本获胜时
  必须在同一协调写区间内先调用该 `NSFileVersion` 的替换 API 恢复目标文件，再回读验证当前字节；
- 获胜内容成为当前文件并验证成功后，才能把被淘汰版本标记为已解决并移除其他版本；
- 校验阶段记录文件版本的持久标识；进入最终协调写区间后重新枚举并核对获胜版本，标识或内容
  已变化时放弃本轮决策并重新预检，避免校验与执行之间的竞态；
- 凭据副本继续只自动消除字节完全相同的冲突，不套用 manifest 的版本向量规则。

测试与非 iCloud 文件系统使用确定性的本地实现，避免单元测试依赖实时 iCloud 状态。

### Core：持久化发布台账

为当前设备的新快照增加本地 SQLite 发布台账，记录 store ID、device ID、generation、
revision、确定性快照目录、三个快照摘要、manifest 摘要、状态及取代它的已确认 revision。
状态机只有以下路径：

- `prepared`：快照已校验，但从未进入 manifest 替换，可立即回收；
- `publicationUncertain`：进入替换前必须先持久化该状态，任何异常或进程退出后仍持续保护；
- `published`：manifest 已协调回读且摘要相同，允许确认对应 outbox；
- `superseded`：更高 revision 的 manifest 已确认发布，并包含未确认 outbox 重新合并的结果，
  旧快照才取得回收资格。
- `reclaimed`：`superseded` 快照目录已物理回收，但台账记录继续保留，作为迟到 manifest 的
  作废证据；该状态不再进入清理候选。

台账状态转换和本地 revision/outbox 确认放在同一数据库事务边界。缺少台账、摘要不匹配或状态
不合法时一律保留快照。所有者处理延迟到达的旧 manifest 时，只有其完整 manifest 摘要、
snapshotDirectory 和快照摘要与 `superseded` 台账逐项相同，且当前更高版本完整有效，才能在
旧快照已回收的情况下把该文件版本认定为已确认祖先；物理回收后记录转为 `reclaimed` 而不
删除，否则迟到版本会失去验证证据。任一字段不符仍按普通冲突保留。

### Coordinator：单写者与调度

每次同步周期和每个清理批次开始前，对按标准化同步根目录摘要派生的本地锁文件尝试获取非阻塞
独占锁。同步周期在完成发布后释放；清理批次在重新构建或核对保护集合、枚举和删除全部结束后
释放。未获得锁的进程跳过本次写入并按正常间隔重试，保证不同进程不会同时发布或清理同一
副本。进程内现有串行队列和 `isSyncing` 代际保护继续保留。

## 幂等发布流程

1. 在创建快照前，协调读取 manifest 并预处理未解决文件版本。
2. 如果冲突无法安全收敛，立即停止发布，不创建任何新快照。
3. 根据即将发布的数据计算快照哈希和确定性 revision 标识；同 revision 的有效快照已存在时
   直接复用，不再生成随机重复目录。
4. 将缺失快照写入临时目录，完成解码、头部和哈希校验后再原子移动为最终目录，并持久化
   `prepared` 台账记录。
5. 在进入确切 manifest URL 的协调替换前，先提交 `publicationUncertain`；随后重新检查文件
   版本。若云端版本与本轮 draft 的 schema、设备、generation、revision、版本向量、快照摘要
   和目录相同，则即使 `updatedAt` 或设备显示名不同也视为同一发布并返回
   `alreadyPublishedDraft`；若存在更高但内容不同的安全版本，返回
   `adoptedNewerRemote`，只追平 revision、失效观察缓存并安排补跑，不发布旧指针。
6. 发布 manifest 后协调回读，验证内容与引用快照，再提交本地 revision。
7. `prepared` 阶段失败可删除本周期新建快照；进入 `publicationUncertain` 后的任何失败都不得
   删除最终快照，后续周期复用同一目录并通过文件版本对账更新台账状态。

发布结果必须区分 `publishedDraft`、`alreadyPublishedDraft` 和 `adoptedNewerRemote`。只有前两类
能够确认本轮 outbox；`adoptedNewerRemote` 不得调用 `acknowledgeSnapshot`，也不得把本地
`finalBundle` 写入远端观察缓存，必须重新读取远端状态并用仍保留的 outbox 重新合并。

快照目录名称保留 generation 和 revision，并以三个快照内容哈希的组合摘要代替随机 UUID，
从目录层面保证相同 revision、相同内容的重复调用落到同一目标。若相同 generation/revision
出现不同摘要，保留两者并将其视为待判定分叉，禁止覆盖。

## 现有冲突与孤儿目录恢复

同步启动和每次周期预检只对当前设备拥有的副本运行安全收敛逻辑。对当前 1885/1887 场景，
1887 是唯一支配版本且所有快照校验通过，因此在发生冲突的设备升级后，由该设备选择 1887、
标记 1885 已解决，再让本地 revision 从当前 manifest 追平。其他设备只读该副本并报告冲突，
不能代替所有者修复。若现场数据在执行前发生变化，必须重新校验，不能沿用本次诊断结论。

所有者设备无法运行时，跨设备维修只能作为显式人工操作：先停止所有设备写入、重新校验全部
文件版本和快照、展示将保留及删除的精确版本，再经人工确认执行；该维修入口不属于自动同步
周期，也不能放宽日常“只写自己的副本”约定。

自动回收不按目录全量扫描推断孤儿，只从本地台账读取当前副本中明确为 `prepared` 或
`superseded` 的记录；`publicationUncertain`、无台账目录和摘要不匹配目录永久排除。每次发布
成功后，在同一个跨进程锁周期内最多处理 256 条记录且总耗时不超过 2 秒。`prepared` 只可能在
快照写完但尚未进入 manifest 替换时产生；进入替换前状态已持久化为 `publicationUncertain`，
因此它不可能被已发布 manifest 引用。`superseded` 即使稍后收到迟到 manifest 文件版本，也能
通过逐项匹配的台账证据被解析器认定为输家，不需要保留旧快照内容。

清理遇到目录、删除或 File Provider 错误时立即停止，剩余台账记录由后续正常发布周期继续
处理。当前 manifest 指向的目录始终作为额外保护项排除；清理不枚举或删除未登记目录，也不
跨设备副本。

该清理器不得跨设备目录，不得在 manifest 不完整时运行，也不得把“目录较旧”单独作为
删除依据。

现有 UUID 快照没有发布台账，不能自动判定为孤儿。当前实现只阻止新的重复目录继续增长，并
永久保留这些历史目录；没有提供历史 UUID 目录的枚举、隔离或删除入口。是否增加显式维修工具
及其授权、两次稳定观察、可恢复隔离和删除确认流程均为待确认事项，不能由日常同步自动执行。

## 失败处理与可观察性

安全可收敛的冲突自动恢复；真正分叉、损坏或未下载完成的冲突保留原文件版本，并向设置页
报告“同步数据存在版本冲突”，不再用笼统的同步失败覆盖原因。手动同步可立即重试，后台
重试仍遵循现有周期，但预检保证重试不会创建新快照。

当前实现通过独立同步状态向设置页报告冲突，没有新增包含现场计数的诊断日志。若后续增加诊断
遥测，日志不得记录设备名称、剪贴板内容、凭据、真实路径或完整设备 ID。

## 兼容性与迁移

manifest schema 和同步目录顶层结构保持不变。读取端继续兼容现有 UUID 快照目录；确定性
目录名只用于新发布。现有本地 revision 仍通过当前 manifest 取最大值追平。新增本地发布台账
需要 SQLite 迁移；旧数据库升级时创建空表，空台账采用“只保留、不自动删除”的安全默认值，
并提供迁移与回滚读取测试。旧版本客户端仍能读取新 manifest 和其引用的快照，但无法执行新的冲突恢复；因此
真实云端恢复时应先暂停其他设备写入并升级发生冲突副本的所有者设备，再逐台升级恢复；所有者
无法运行时，使用前述显式人工跨设备维修流程。

## 验证方案

自动化验证覆盖：

- 1885/1887 祖先关系选择 1887，并拒绝不同 generation、不同设备和不可比较分叉；
- 当前文件获胜和未解决冲突版本获胜都能生成正确的当前文件，且回读后才移除其他版本；
- 未解决候选内容通过各自 `version.url` 协调读取，执行前版本变化会放弃旧决策；
- 自身 `seenRevisions` 缺失、小于 revision、负数或赢家 revision 回退时禁止自动收敛；
- 缺失、损坏、未下载或哈希错误的快照禁止自动消除冲突；
- `verifiedBySupersededLedger` 只淘汰摘要逐项匹配的迟到祖先，不能成为赢家、参与合并或确认 outbox；
- manifest 预检失败时快照目录数量不变；
- 同 revision、同内容连续重试只产生一个快照目录；
- manifest 替换开始前失败可回收 `prepared` 快照，开始后失败会持久化
  `publicationUncertain` 并在重启后继续保护；
- manifest 已替换但回读失败时不删除快照，后续对账能识别已经发布的 draft；
- 快照先到、引用它的 manifest 在清理批次结束后才到达时，台账保证快照仍存在；
- `adoptedNewerRemote` 不确认 outbox、不写入错误观察缓存，并能补跑发布本地变更；
- 台账清理只处理 `prepared` 或 `superseded`，并共同遵守 256 个和 2 秒上限；已删除的
  `superseded` 记录转为 `reclaimed`，迟到 manifest 仍能匹配证据且不会重复进入清理；
- 两个协调器竞争同一写锁时只有一个进入发布区间；
- 无台账 UUID、`publicationUncertain` 和摘要不匹配目录不会进入自动删除清单；
- SQLite 发布台账从旧数据库安全迁移，状态转换与 outbox 确认具备事务回滚测试；
- 只有副本所有者自动恢复和清理，其他设备保持只读并报告冲突；
- Coordinator 能把不可收敛冲突映射为独立状态，Core 状态文案测试显示预期提示；
- 旧 UUID 目录、旧 manifest 和现有同步合并测试继续通过。

实现后依次运行聚焦测试、完整 `swift test`、严格并发构建和打包验证。真实 iCloud 验证需使用
打包应用：先在隔离副本重放 1885/1887 文件版本、真正分叉和重复失败，确认设置页能区分
“同步数据存在版本冲突”与普通失败；再经人工确认后对实际同步目录执行一次恢复，确认冲突
消失、下一 revision 单调增加且重复失败不再增加目录，并观察另一台设备能够读取恢复后的指针。
历史目录维修能力尚未实现，本方案不会对它们执行隔离或删除。

## 验收标准

- 可证明的祖先冲突自动收敛，分叉冲突保持原状并显示明确状态；
- 任意重复失败次数下，同 revision 快照目录数量保持有界；
- 重启和多进程竞争不会产生并发 manifest 写入；
- 自动清理只删除台账证明从未发布或已被确认取代的快照，不删除结果不确定或历史无台账目录；
- 同步协议 v1、剪贴板筛选和大小写内容语义不发生变化；
- 自动化、严格并发、打包和经确认的真实 iCloud 验证均有可复现证据。
