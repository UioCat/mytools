# GitHub Release 自动更新设计

## 目标

为 MacTools 增加应用内更新入口，使安装过首个更新版本的用户能够从 GitHub Release 安全检查、下载并安装后续版本，无需手工替换应用。方案不依赖 Apple Developer Program 付费能力，继续使用当前 GitHub 仓库和 Release 工作流。

成功标准如下：

- “设置 → 通用”显示当前版本、手动检查更新和自动更新选项；
- 默认每天自动检查一次，发现新版本后由用户确认安装；
- 用户可以选择由 Sparkle 自动下载并在应用退出时安装更新，该能力默认关闭；
- 下载内容必须通过 HTTPS 和 Sparkle EdDSA 签名双重校验，校验失败时拒绝安装；
- GitHub Release 同时发布 DMG、SHA-256 和 `appcast.xml`，应用只从稳定 Release 更新；
- 大版本变更和用户可感知的缺陷修复在验证通过后自动创建版本标签并发布 Release；
- 首个支持更新的版本发布后，本机运行的应用替换为相同正式版本。

## 现状与约束

当前 `.github/workflows/release.yml` 在推送 `v*` 标签后构建临时签名的 `.app`，制作 DMG，并将 DMG 与 SHA-256 上传到 GitHub Release。应用本身不包含更新框架，Release 也没有更新源和独立的软件包签名。

`scripts/package_app.sh` 通过 SwiftPM 产物手工组装应用包，尚未处理第三方动态 framework 和嵌套 helper。设置界面位于 `MacToolsCore`，按架构约定不能直接引用 Sparkle、网络或具体平台实现。

应用当前采用 ad-hoc 代码签名。该方式不产生费用，但无法提供 Developer ID 身份连续性：macOS 可能在版本替换后要求用户重新确认打开应用，辅助功能、输入监控或屏幕录制权限也可能需要重新授权。Sparkle 的 EdDSA 签名可以验证更新包由本项目发布，但不能替代 Apple 的 Developer ID 签名和公证。

## 方案比较

| 方案 | 更新体验 | 安全与维护成本 | 结论 |
| --- | --- | --- | --- |
| Sparkle 2 + GitHub Release | 完整检查、下载、安装和重启流程 | 成熟框架；需要调整打包和发布 | 采用 |
| GitHub API + 打开 DMG | 只能提示并跳转下载 | 实现简单，但仍需手工替换 | 不满足自动更新目标 |
| 自研下载与应用替换器 | 可定制完整流程 | 签名校验、权限、进程交接和失败恢复风险高 | 不采用 |

## 当前方案

### 运行时架构

通过 Swift Package Manager 引入 Sparkle 2。可执行层新增更新服务并持有 `SPUStandardUpdaterController`，负责检查周期、更新源、下载、安装和标准更新窗口。设置界面只接收普通状态和动作闭包，不直接导入 Sparkle。

| 组件 | 职责 |
| --- | --- |
| `SystemUpdateService` | 位于 `Sources/MacTools/Platform/Updates`，封装 Sparkle updater、当前更新状态和偏好读写 |
| 应用运行时装配 | 位于 `Sources/MacTools/Application`，创建服务并向设置页面注入状态和动作 |
| `SettingsView` | 显示当前版本、检查按钮和两个自动更新开关，不直接访问网络或更新框架 |
| Sparkle 标准界面 | 展示版本说明、进度、错误以及需要用户参与的安装与重启流程 |

更新偏好由 Sparkle 使用本机 `UserDefaults` 管理，不写入 MacTools 的 iCloud 设置同步。不同 Mac 可以独立决定是否自动检查和下载，避免一台设备的安装策略影响其他设备。

### 设置入口与行为

“设置 → 通用”增加独立的“软件更新”区域：

| 项目 | 默认值 | 行为 |
| --- | --- | --- |
| 当前版本 | 只读 | 显示 `CFBundleShortVersionString` 和构建号 |
| 检查更新 | 可用 | 立即启动 Sparkle 标准检查流程 |
| 自动检查更新 | 开启 | 每天检查一次稳定更新源 |
| 自动下载并安装更新 | 关闭 | 开启后允许 Sparkle 后台准备更新，并在应用退出时自动安装；需要授权时仍由系统提示 |

手动检查始终可用。无新版本时明确提示已经是最新版；网络、更新源和签名错误使用 Sparkle 标准错误流程呈现。手动检查不会在用户未确认时退出或重启；只有用户主动开启“自动下载并安装更新”后，Sparkle 才可以在应用退出时完成后台安装。

### 版本与更新源

稳定更新源使用 GitHub Release 的固定地址：

```text
https://github.com/UioCat/mytools/releases/latest/download/appcast.xml
```

每个稳定 Release 的 `appcast.xml` 至少包含：

- 与 Git 标签一致的语义版本，例如 `0.2.0`；
- 单调递增的数字构建号；
- 最低系统版本 macOS 26；
- DMG 的 HTTPS 下载地址、文件长度和 Sparkle EdDSA 签名；
- 面向用户的版本说明。

`CFBundleShortVersionString` 取去掉 `v` 前缀的标签版本，`CFBundleVersion` 使用 GitHub Actions 的递增构建号。应用只消费正式发布的稳定 Release，不把草稿或预发布版本暴露给默认更新源。

### 签名与密钥

首次实施时生成一组独立的 Sparkle EdDSA 密钥：

- 公钥写入应用 `Info.plist` 的 `SUPublicEDKey`，允许进入源码和发布产物；
- 私钥以 GitHub Actions Secret 提供给发布工作流，并在发布者 macOS Keychain 中保留恢复副本；不得写入仓库、明文文件、构建日志或 Release 附件；
- 发布工作流使用私钥为最终 DMG 生成 Sparkle 签名和 `appcast.xml`；
- 应用同时要求 HTTPS 和有效 EdDSA 签名，任一校验失败都不得安装；
- SHA-256 继续作为人工和流水线校验信息，但不替代应用内签名验证。

密钥轮换必须先发布能够信任新公钥的过渡版本，不能直接替换公钥导致已安装版本失去更新链路。当前不引入自定义下载器或应用替换逻辑。

### 构建与打包

`Package.swift` 为 `MacTools` 可执行目标增加 Sparkle 依赖。`scripts/package_app.sh` 需要：

1. 将 Sparkle framework 及其必需 helper 完整嵌入 `Contents/Frameworks`，保留符号链接、可执行权限和目录结构；
2. 在 `Info.plist` 写入更新源、公钥、更新默认值以及真实版本和构建号；
3. 先签名嵌套 framework 和 helper，再签名主应用，继续支持当前 ad-hoc 签名和未来 Developer ID 签名；
4. 校验可执行文件的动态依赖均指向应用包内部，不依赖 `.build` 或开发机路径。

签名流程显式覆盖嵌套组件，不以 `codesign --deep` 代替正确的由内到外签名。`scripts/rebuild_and_run_app.sh` 继续复用同一打包入口，本地正式版本安装时显式传入对应版本和构建号，避免显示默认 `0.1.0`。

### GitHub Release 发布

现有标签触发工作流继续作为唯一正式发布入口，并增加以下阶段：

1. 构建、组装和签名应用；
2. 检查 Sparkle framework、helper、版本字段和签名；
3. 创建 DMG，计算 SHA-256，并生成带 EdDSA 签名的 `appcast.xml`；
4. 以草稿方式创建 Release，上传 DMG、SHA-256 和 `appcast.xml`；
5. 回读并校验三个附件、版本号、下载地址和 appcast 内容；
6. 全部通过后发布正式 Release；任何阶段失败都保留失败状态，不发布不完整版本。

首个包含更新能力的版本定为 `v0.2.0`。`v0.1.5` 及更早版本没有更新框架，无法发现 `v0.2.0`，必须通过现有 DMG 或本地打包方式完成一次手工升级。从 `v0.2.0` 开始，后续稳定版本进入应用内更新链路。

### 自动发布规则

`AGENTS.md` 增加发布约定，将“代码提交并推送”和“面向用户发布”区分处理：

| 变更类型 | 版本策略 | 发布动作 |
| --- | --- | --- |
| 用户可感知的缺陷修复 | 递增补丁版本 | 完成验证、提交和推送后创建并推送 `vX.Y.Z` 标签，等待 Release 成功 |
| 重大用户功能或行为变更 | 递增次版本 | 完成完整验证后创建并推送标签，等待 Release 成功 |
| 文档、测试、内部重构 | 不单独发版 | 只提交并推送；与下一个产品版本合并发布 |

自动发布必须满足适用的聚焦测试、完整 `swift test`、打包检查、敏感信息扫描和人工验证要求。标签推送后需持续检查工作流，确认 Release 不是草稿、三个附件均存在且更新源可读取；失败时报告标签、工作流和未完成项，不宣称发布成功。

### 本机升级与首发验证

`v0.2.0` 发布成功后，用正式发布产物更新本机当前运行的 MacTools，并确认进程路径、设置页版本和构建号与 Release 一致。

由于旧版本没有更新器，首次端到端验证使用同一份更新器代码构建一个较低版本和构建号的测试应用，让它读取已经发布的 `v0.2.0` 稳定源并执行真实升级。测试应用使用独立路径和设置域，避免覆盖正式应用偏好；升级完成后确认应用重新启动且版本到位。测试产物不上传 Release、不加入源码控制。

## 错误与边界

| 场景 | 处理 |
| --- | --- |
| 网络不可用或 GitHub 限流 | 保留当前版本并提示失败；下个检查周期重试 |
| `appcast.xml` 无效或附件缺失 | 工作流不发布；客户端拒绝该条目 |
| EdDSA 校验失败 | 拒绝安装并显示错误，不允许绕过 |
| 应用包不可写或替换失败 | Sparkle 报错并保留当前可运行版本 |
| 更新后系统权限失效 | 设置中的权限诊断继续引导用户重新授权 |
| 用户关闭自动检查 | 不执行定时检查，仍保留手动检查入口 |

免费方案不承诺 Developer ID 签名带来的首次打开、Gatekeeper 和 TCC 身份连续性。后续如果加入 Apple Developer Program，只替换代码签名与公证阶段，不改变 Sparkle、appcast 和设置入口架构。

## 测试与验证

### 自动测试

在 `MacToolsCoreTests` 和脚本检查中覆盖：

| 场景 | 预期 |
| --- | --- |
| 设置页更新状态 | 当前版本和构建号正确，按钮与开关调用注入动作 |
| 服务状态映射 | 检查中、可更新、无更新和错误状态稳定映射到 UI |
| 偏好切换 | 自动检查和自动下载写入 Sparkle 偏好并即时生效 |
| 应用包结构 | Sparkle framework/helper、更新配置和版本字段完整 |
| 动态依赖 | 主程序和 helper 不引用开发机临时路径 |
| 发布工作流 | appcast 包含版本、构建号、DMG URL、长度和 EdDSA 签名 |
| 密钥保护 | 源码、日志和 Release 附件不包含私钥 |

先运行新增的聚焦测试，再运行完整 `swift test`。

### 打包与端到端验证

1. 运行 `scripts/package_app.sh`，检查应用包结构、嵌套签名、`Info.plist` 和动态链接路径；
2. 启动打包应用，在“设置 → 通用”执行手动检查，验证无新版本提示和自动更新开关持久化；
3. 推送 `v0.2.0` 后等待 GitHub Actions 完成，验证 DMG、SHA-256、`appcast.xml` 及其公开下载地址；
4. 使用较低版本测试应用检查、下载、安装并重启到 `v0.2.0`；
5. 重新检查辅助功能、输入监控和屏幕录制权限状态，记录是否需要重新授权；
6. 使用正式 Release 更新本机应用，确认设置页版本、进程路径和既有窗口布局修复均生效。

发布完成的判定依据是客户端能够验证并安装真实 Release，而不只是工作流成功或应用编译通过。
