# 窗口布局自适应写入与回读校验设计

## 目标

修复窗口从三分之一等布局切换到二分之一或最大化时，只更新位置、尺寸未到位的偶发现象。窗口布局操作必须以系统最终实际 `frame` 为成功依据，在目标应用延迟处理或部分拒绝 Accessibility 写入时进行有限恢复，同时避免无限重试、旧请求覆盖新请求和重复改写已经到位的属性。

成功标准如下：

- `rightThird → rightHalf`、`rightThird → maximize` 等放大场景最终位置和尺寸均在 `1 pt` 容差内；
- 缩小、仅移动和混合尺寸变化采用与变化方向匹配的写入顺序；
- 位置或尺寸只有一项未到位时，后续只重写该项；
- 单次请求最多执行 3 轮写入，并在 `120 ms` 总时限内结束；
- 快速连续触发时只允许最新请求继续回读和重试；
- 只有回读确认到位后才记录布局应用成功。

## 现状与根因

macOS Accessibility API 没有原子设置窗口 `frame` 的接口，应用只能分别写入 `kAXPositionAttribute` 和 `kAXSizeAttribute`。目标应用可以在两次写入之间执行自身的窗口约束、动画或布局修正，因此一次调用成功不代表最终位置和尺寸同时符合目标。

当前主分支的 `SystemWindowLayoutService` 使用固定的“尺寸 → 位置 → 尺寸”顺序，忽略各次 `AXUIElementSetAttributeValue` 的返回值，并在写入后直接记录成功。截图中的 `rightThird → rightHalf` 结果表现为横坐标已从屏幕约 `2/3` 移到 `1/2`，宽度仍保持约 `1/3`，符合“位置写入生效、尺寸写入未最终保留”的部分应用特征。

仅增加固定延迟后重写完整 `frame` 仍有三个问题：

| 问题 | 影响 |
| --- | --- |
| 写入顺序固定 | 放大和缩小受到目标应用约束时需要的安全顺序不同 |
| 完整重写 | 已到位的属性可能再次触发目标应用布局，制造新的偏差 |
| 只按调用次数判断 | 无法区分写入返回成功、系统延迟生效和最终值被目标应用改回 |

## 方案比较

| 方案 | 可靠性 | 复杂度 | 结论 |
| --- | --- | --- | --- |
| 固定顺序写三次 | 低 | 低 | 无法判断最终结果，保留当前缺陷 |
| 固定延迟后重写完整 `frame` | 中 | 低 | 能覆盖部分延迟，但会重复扰动已到位属性 |
| 持续轮询直到成功 | 高 | 高 | 生命周期和资源边界不清晰，可能形成后台重试 |
| 自适应顺序、回读校验、按失败部分有界重试 | 高 | 中 | 采用；可靠性和复杂度最平衡 |

## 当前方案

### 自适应写入顺序

每轮都以最近一次回读的实际 `frame` 和目标 `frame` 生成写入计划，不沿用首次请求时的旧尺寸。

| 实际值与目标值 | 写入计划 | 原因 |
| --- | --- | --- |
| 仅位置不一致 | 只写位置 | 不触碰已经正确的尺寸 |
| 仅尺寸不一致 | 只写尺寸 | 不触碰已经正确的位置 |
| 宽高均为放大或保持 | 位置 → 目标尺寸 | 先把窗口锚定到目标区域，再向可用区域内扩展 |
| 宽高均为缩小或保持 | 目标尺寸 → 位置 | 先释放窗口占用范围，再移动到目标位置 |
| 一个维度放大、另一个维度缩小 | 收缩维度的中间尺寸 → 位置 → 目标尺寸 | 先完成不会扩大占用范围的变化，再移动并补齐放大维度 |

位置和尺寸比较分别使用 `1 pt` 容差。尺寸相等时不执行多余写入；中间尺寸按每个维度的 `min(actual, target)` 计算。

### 回读与按项校验

每轮写入后，服务在下一显示周期开始独立回读 `kAXPositionAttribute` 和 `kAXSizeAttribute`，保留每一项成功取得的结果，再分别计算：

- `positionMismatch`：`minX` 或 `minY` 超出容差；
- `sizeMismatch`：`width` 或 `height` 超出容差。

两项均匹配时立即结束并记录成功。只有一项不匹配时，下一轮仅生成该项的写入命令；两项都不匹配时，基于最新实际值重新计算自适应顺序。某一属性回读失败时，该属性标记为 `unknown` 并进入后续重试判断，另一项已经回读匹配的属性不会被重复写入。服务不会伪造实际值或提前更新布局状态。

### 有界重试

单个布局请求同时受写入轮数和总时限约束：

| 参数 | 取值 |
| --- | ---: |
| 最大写入轮数 | `3` |
| 首次回读间隔 | 约一个显示周期，`16 ms` |
| 总时限 | `120 ms` |
| frame 容差 | `1 pt` |

回读使用主线程异步调度，不阻塞事件处理。每次回读一旦满足目标立即结束；未满足且仍有写入额度时，只重试不匹配项；写入轮数耗尽后可以继续回读到总时限，但不再写入。达到总时限仍未到位时记录失败并结束，不创建常驻定时器。

### 请求代次与状态提交

`SystemWindowLayoutService` 在主 Actor 上维护一个递增的请求代次和当前验证任务。每次新的快捷键或面板操作都会：

1. 增加代次并取消旧验证任务；
2. 保存本次窗口元素、目标布局和目标 `frame`；
3. 从最新实际 `frame` 启动首轮写入。

所有延迟回读在执行前检查代次，旧请求即使已经排入主队列也不能继续写窗口或提交状态。请求采用“最新操作全局优先”，不使用 `windowID ?? 0` 作为异步任务键，避免无法取得窗口 ID 时不同窗口共享状态。窗口 ID 不可用时仍可完成当前 AX 操作，但不写入按窗口缓存的布局循环状态。

`appliedLayoutsByWindowID` 只在回读确认成功后更新。为保持多布局快捷键的连续切换，尚在验证中的最新请求可以作为下一次循环选择的候选状态，但不能作为已成功应用状态或成功日志依据。

### 错误与日志

每次 AX 写入和回读都保留具体 `AXError`。日志只记录布局 ID、请求代次、轮次、失败组件、AX 错误码和最终状态，不记录窗口标题或其他用户内容。

最终状态分为：

| 状态 | 条件 |
| --- | --- |
| `applied` | 实际位置和尺寸均在容差内 |
| `cancelled` | 被更新的请求代次替代 |
| `timedOut` | 轮数或总时限耗尽后仍未到位 |
| `readFailed` | 总时限内始终无法读取完整实际 `frame` |

单次 `AXError.cannotComplete` 不直接终止请求，由后续回读决定是否需要重试；参数非法、属性不支持等确定性错误不重复写同一属性，但仍回读另一属性的最终状态。

## 组件边界

| 组件 | 职责 |
| --- | --- |
| `WindowFrameApplicationPolicy` | 在 `MacToolsCore` 中提供尺寸变化分类、写入计划、分项容差判断和重试边界；保持为纯逻辑 |
| `SystemWindowLayoutService` | 在主 Actor 上执行 AX 读写、异步调度、请求取消、日志和成功状态提交 |
| `WindowLayoutCalculator` | 继续只负责从布局和屏幕可见区域计算目标 `frame`，不感知 AX 重试 |

不引入新的通用窗口框架，不修改布局计算公式、快捷键配置和窗口循环产品规则。

## 测试与验证

### 自动测试

在 `WindowLayoutCalculatorTests` 或独立策略测试中覆盖：

| 场景 | 预期 |
| --- | --- |
| `rightThird → rightHalf` | 首轮计划为位置 → 尺寸 |
| 最大化 → 居中 | 首轮计划为尺寸 → 位置 |
| 仅位置失败 | 下一轮只有位置写入 |
| 仅尺寸失败 | 下一轮只有尺寸写入 |
| 混合放大与缩小 | 先中间尺寸，再位置和目标尺寸 |
| `1 pt` 内系统取整 | 判定成功，不重试 |
| 连续新请求 | 旧代次不能产生后续写入或成功提交 |
| 持续不匹配或回读失败 | 最多 3 轮写入，并在总时限结束 |

先运行窗口布局聚焦测试，再运行完整 `swift test`。

### 打包应用验证

使用 `scripts/rebuild_and_run_app.sh` 构建并启动打包应用，在 Chrome 和至少一个原生 AppKit 应用中验证：

1. `rightThird → rightHalf` 与 `rightThird → maximize` 连续各执行至少 20 次，确认无只移动不放大；
2. 覆盖最大化到居中、左右半屏互换、仅移动以及快速连续切换；
3. 在当前显示器上通过面板和已配置快捷键分别触发；
4. 检查日志中的成功记录均有回读依据，失败请求在 120 ms 内结束；
5. 多显示器可用时覆盖不同缩放比例和可见区域，确认目标 `frame` 仍由当前显示器计算。

无法取得辅助功能权限、目标应用拒绝设置尺寸或系统强制最小窗口尺寸时，允许请求以失败状态结束；不得记录为成功，也不得持续重试。
